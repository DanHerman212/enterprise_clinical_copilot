# §3 — MCP Server + Cross-Patient Isolation

## Scope

This section covers the MCP server in `projects/agent-harness/mcp_server/`: the three tools the agent calls — `predict_readmission`, `rag_search`, and `rag_search_sections` — and, above all, the **R1 cross-patient isolation boundary** they collectively enforce. It is the crown jewel of the review: everything the agent knows about a patient flows through these tools, so a defect here is not a bug but a breach — one patient's clinical text cited under another's admission. The server is transport-agnostic (stdio for local and Claude Desktop, streamable-HTTP on Cloud Run, stateless by default — the tools hold no per-session state), with shared configuration in `config.py` and a cached Vertex endpoint handle resolved once per process.

The prediction tool takes an admission id, fetches the feature row through a Protocol seam over BigQuery (the value parameterized, the result restricted to the manifest's feature order so label and bookkeeping columns can never silently reach the model), orders the vector, and calls the Vertex endpoint — returning probability, threshold, decision, and the top contributing factor groups, with every failure a structured error dict rather than an exception. Retrieval embeds the query (gemini-embedding-001, 768-dim) and queries Vertex Vector Search with the admission restrict applied *inside* the index query as a `Namespace("hadm_id", …)` filter — server-side, not a post-filter. Passage text is resolved by note id in one batched BigQuery query and deterministically re-chunked so a citation returns the exact section chunk rather than the whole note. A section-anchored retry re-queries with the section's actual body text when a clearly section-targeted query fails to rank its section first. The third tool is deterministic by construction: it fetches the note by admission id, re-parses it with the same chunker that built the index, and returns one passage per major summary section — full recall with no top-k luck.

The isolation model, verified during the review: prediction and section coverage are isolated by their single-row admission fetch; `rag_search` is isolated by the in-query Namespace restrict, with text resolution *trusting* that restrict — no re-check that a resolved note belongs to the requested admission. All data is synthetic (`hybrid_features`, `hybrid_notes`); the real MIMIC tables are explicitly out of scope.

## Adversarial Review Pass

§3 ran under the **both protocol** — the highest-assurance track: an independent adversarial model performed a blind hostile pass on the raw files *and* a cross-check pass attempting to falsify the primary reviewer's understanding, with findings merged afterward. The headline result is what survived: **R1 held.** The adversarial pass confirmed the restrict is genuinely in-query, that section coverage is isolated by its admission fetch, and that the bandit B608 SQL-injection hit (ECC-01) is a false positive — every user value is parameterized; only config constants are interpolated. Twelve findings resulted (ECC-19…ECC-30). The dominant theme is that the *core* isolation and error discipline are sound, but the machinery layered on top of retrieval — the section-anchored retry, the passage-resolution fallbacks — can silently destroy correctness, and one of those paths is the section's lone Critical.

### The retry machinery is the section's liability

- **ECC-20 · Critical (ops/spend, DoS).** The section-anchored retry recurses with no depth guard: it re-enters the search with the section's own body text, which itself contains the trigger word, so a query that persistently fails to rank the target first re-fires the same branch — and the note is re-fetched uncached at every level. Every level is a billed embed, a Vector Search query, and one to two BigQuery queries; a single adversarial or merely unlucky query can generate thousands of billable calls before hitting Python's recursion limit. Upgraded to Critical by the adversarial pass as an attacker-triggerable spend amplifier. *Remediate:* pass an explicit depth/retry flag permitting exactly one anchored retry, skip anchor computation on the retry path, and cache the section bodies per request.
- **ECC-24 · Major (correctness).** The retry returns its result whenever the retried payload carries no error key — but an honest empty result (`returned: 0`) has no error key either, so a non-empty original result is discarded in favor of zero passages. A mechanism meant to improve ranking destroys recall. *Remediate:* return the retried result only when it returned at least one passage; otherwise fall through to the original neighbors.
- **ECC-30 · Minor (correctness).** The wrong-rank trigger's three clauses reduce to a single live one — the anchor not being rank 1 — so the expensive retry fires even when the anchor sits at rank 2, a broader and costlier trigger than the "absent from top-k" intent the comment states. *Remediate:* decide the intended trigger, implement it explicitly, delete the dead clauses.

### Isolation is real but single-layered

- **ECC-19 · Major (security).** R1 rests on exactly one enforcement point: the index Namespace filter. Text resolution then resolves passages by note id with no re-check that the note belongs to the requested admission. The design is fail-closed if the restrict is misconfigured (missing namespaces exclude datapoints), but any upstream defect — a wrong or missing restrict token, a stale index, a datapoint-id parsing truncation — flows straight through to another patient's section text. *Remediate:* add the admission id to the text-resolution query and hard-error with `isolation_violation` if any resolved admission differs — a second, independent enforcement of R1 at the BigQuery layer.
- **ECC-25 · Major (security).** The HTTP transport has no app-layer auth and no per-principal authorization: nothing binds a caller to a permitted admission, so isolation is per-request, not per-principal. The posture rests entirely on Cloud Run IAM being right at deploy; a single `--allow-unauthenticated` exposes the full dataset and the billable Vertex/BigQuery surface — compounding the ECC-20 recursion into an unauthenticated cost-amplification vector. *Remediate:* enforce no-unauthenticated deployment (verify the platform-injected identity header in middleware); beyond a demo, add a caller-to-permitted-admissions mapping.
- **ECC-22 · Minor (correctness).** The tools never restrict to the demo cohort — any admission id present in the feature or notes tables works, so a user coming through the public console can probe beyond the 24-patient cohort. The data is synthetic, but the cohort boundary is enforced nowhere server-side; this is the same gap the §1 review flagged from the other end (S1-09). *Remediate:* enforce cohort membership as the authorization boundary, or document that the tables hold only demo rows.

### Passage resolution can silently lie

- **ECC-23 · Major (correctness).** A datapoint id that fails the known-section pattern parses to a null note id and section, and the passage is appended with *null text* — the error path is skipped precisely because the note id is null. The known-sections list is a hand-maintained 13-name copy of a chunker vocabulary that recognizes roughly 29, so any indexed section outside the 13 hits this path: a malformed or foreign index id reaches the model as a null-text citation instead of an error — the exact silent drop the `missing_text` guard exists to prevent. *Remediate:* return a structured error (or skip and flag) when the note id is null, and derive the section vocabulary from the chunker's canonical names rather than a duplicate literal.
- **ECC-26 · Minor (correctness).** When a chunk id fails to reproduce at serving time, the passage body falls back to the *entire note* — silently, with no granularity marker — which happens systematically if the index was built with chunker parameters the serving path doesn't know (they are recorded nowhere), and the fallback's `or` also treats a legitimately empty chunk as missing. This is precisely the whole-note leakage into a citation that the module's own docstring says it prevents. *Remediate:* use an explicit `is None` check, tag or error on fallbacks, and pin the chunker parameters used at index build.
- **ECC-27 · Minor (correctness).** Both note queries use `LIMIT 1` with no `ORDER BY`; BigQuery guarantees no ordering, so an admission with multiple note rows yields a nondeterministic note — section coverage could cite a different note across calls, and the anchored retry could anchor on a note different from the one the index matched. *Remediate:* add a deterministic ordering (or aggregate the admission's notes) and consider asserting the single-note assumption.

### Input validation and operational hygiene

- **ECC-28 · Minor (correctness).** Admission-id validation is inconsistent across the three tools: retrieval checks for a positive integer, but prediction and section coverage perform none — a non-integer (or a `bool`, which passes an integer isinstance check) reaches the BigQuery binding and surfaces as an opaque fetch-failure string instead of a clean bad-request. *Remediate:* extract the validation into a shared helper applied at all three entry points, rejecting booleans.
- **ECC-29 · Minor (security).** Table identifiers from environment variables are interpolated into SQL with no validation or allowlist. User values are parameterized (verified), but an operator-controlled variable could inject arbitrary SQL or — more realistically — silently repoint the demo at the real MIMIC tables the config's own comments say must never be served. *Remediate:* validate table names against a strict pattern at import, or allowlist the permitted tables per deployment.
- **ECC-21 · Minor (security).** Every tool error message embeds the raw exception text, which can carry internal table names, project ids, and URLs — and it reaches the *model* (which narrates it to the user) and the observability store. The same theme as the agent layer's disclosure finding (ECC-06). *Remediate:* log detail server-side; return stable error codes with short generic messages in the tool contract.

## Remediation Scope

**Summary.** The strategic read: R1 survived a hostile pass — the restrict is in-query, section coverage is structurally isolated, and the SQL-injection scan hit was disproven — but the boundary is *thinner* than it should be, and the retrieval embellishments are where the real danger lives. The recommended order is (1) **cap the recursion** — ECC-20 is the section's only Critical and the only attacker-triggerable unbounded-spend path, and its fix (one explicit retry, cached section bodies) also naturally carries the ECC-24 recall fix and the ECC-30 trigger cleanup, since all three live in the same dozen lines; (2) **make R1 two-layered** — ECC-19's admission re-check at text resolution converts every upstream index defect from a silent breach into a hard `isolation_violation`, and ECC-25's deploy-time auth verification protects the layer beneath it; (3) **stop the silent citation lies** — ECC-23's null-text passages and ECC-26's whole-note fallback both replace the honest-error discipline the module was built on with plausible-looking wrong output, the worst failure mode for a grounding system; (4) **sweep the minors** — shared id validation, table-name allowlisting, generic error messages, deterministic note selection, and the cohort boundary (executed jointly with §1's S1-09).

**Detail.** The retry cluster resolves in one change set: a depth flag threaded through the search entry permitting exactly one anchored retry, anchor computation skipped on the retry path, section bodies cached per request, `retried` returned only when it produced passages, and the trigger rewritten to its intended absent-from-top-k form with the dead clauses deleted. The isolation hardening is a two-line query change — fetch admission id alongside note id and text, parameterized, and hard-error on any mismatch — plus middleware that verifies the platform-injected identity header so an `--allow-unauthenticated` misdeploy fails loudly rather than serving. Citation integrity requires the datapoint-id parser to emit a structured error (or a flagged skip) on unparseable ids, the section vocabulary derived from the chunker's canonical names, the chunk-text fallback replaced with an explicit null check that tags or refuses note-granularity output, and the build-time chunker parameters recorded and threaded into serving. The remaining minors are each small and independent: a shared `hadm_id` validator rejecting booleans at all three entry points, an import-time table-name allowlist, stable error codes with server-side detail logging, an `ORDER BY` on both note queries, and server-side demo-cohort enforcement as the authorization boundary. ECC-01 is closed — verified false positive, every user value parameterized — and needs no action.
