# §5 — IAM / Secrets / Deployment

## Scope

This section covers the production deployment topology across both repos: how the system gets to production, who it runs as, and where its secrets live. The runtime shape is three Cloud Run services — the Django site is the only public surface, deployed by its Cloud Build pipeline (build → push → migrate job → cohort-seed job → deploy) under a dedicated `website-sa` service account; the agent and MCP server sit behind IAM invoker bindings, reachable only via per-request ID tokens minted from the metadata server. Behind them are the two Vertex endpoints that constitute the billable-by-hour footprint: the prediction endpoint (~$80/mo), deployed by a content-addressed CPR script that auto-discovers the newest serving bundle from Model Registry provenance, and the RAG Vector Search endpoint (~$68/mo on the synthetic index). A parallel stand-up script brings both online; `teardown.py` — the single biggest cost lever — takes them down while preserving the registry, index, GCS, and BigQuery state.

Secrets follow a two-track posture: the site pulls its signing key and database password from Secret Manager in production, while Langfuse credentials live in a gitignored, mode-600 env file sourced manually. The `scripts/` bucket is 49 files, but by explicit direction most are one-off development helpers; the review concentrated on the twenty-odd scripts on the production deploy path. Notably, the agent and MCP runtime configuration — model name, MCP URL, observability keys — is not committed anywhere; it exists only as console and deploy-trigger state, a gap the project has flagged as its future-automation direction.

## Adversarial Review Pass

§5 ran under the **blind protocol with scanners**: an independent adversarial model examined the deploy path with no access to the primary pass's conclusions, findings were merged afterward, and automated scanners supplemented the reading. Fourteen findings resulted (ECC-46…ECC-59, with no ECC-52 assigned), plus two cross-section findings — ECC-15 and ECC-36 — whose deployment-relevant aspects were upgraded to Major during this pass and are owned here. The dominant theme is a sharper variant of §1's fail-open story: **the running system is sound, but the repo cannot faithfully or safely recreate it** — configuration lives in console state, defaults point at production, and the reproducibility guarantees the tooling claims do not actually hold.

### The repo cannot recreate production — and what it does recreate is insecure

- **ECC-46 · Critical (ops/security).** Agent/MCP and site runtime env config is unversioned, and the prod/dev switch fails open. `ENVIRONMENT` defaults to `development` — yielding `DEBUG=True`, the insecure fallback `SECRET_KEY`, and SQLite on any deployment missing the var — and no deploy step sets any runtime env (`ENVIRONMENT`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `CLOUD_SQL_CONNECTION_NAME`, `GS_BUCKET_NAME`, `DEMO_AGENT_URL`, `DEMO_FIXTURE_MODE`). Recreating a service from the repo — the exact scenario the cloudbuild comment defends against — produces a public debug site and misconfigured private services. The site half is S1-01; the agent/MCP half lives only in console state. *Remediate:* fail closed (default `production` or hard-fail if unset); declare every env var in the deploy step via `--set-env-vars`/`--env-vars-file`, secrets via `--set-secrets`; codify the agent/MCP deploy in the repo; add a drift check.
- **ECC-15 · Major (security/ops, cross-section §2/§5).** Real production identifiers are committed throughout — GCP project ID and number, bucket, Artifact Registry paths, the numeric Vector Search index ID, a concrete bundle URI with pipeline run IDs, and the private agent's actual Cloud Run URL as a setting default. The full internal topology is reconstructable from source, and it's fail-open: a container started without env vars silently operates against the real project and real BigQuery tables, so local mistakes run against prod by default. *Remediate:* make `PROJECT_ID`/`DEMO_AGENT_URL` required with no production defaults; move real IDs to an untracked env file; audit IAM if the repo goes public.
- **ECC-57 · Minor (correctness).** Environment-override behavior is inconsistent across the deploy scripts: some honor `PROJECT_ID`, others hardcode it — so an operator targeting a second project deploys there while `teardown.py` silently operates against the hardcoded project, leaving resources billing in one project as teardown reports success against another. *Remediate:* one shared config module (or a required env) in every script.

### Deploy sequencing guarantees an outage and risks stranded state

- **ECC-47 · Major (ops).** The CPR deploy undeploys *all* stale models before deploying the new one — a guaranteed serving outage on every redeploy — and if the new deploy fails, the endpoint is left empty with no rollback and the previous deployment config unrecorded. *Remediate:* deploy-first at full traffic, undeploy stale only after success; add a rollback path.
- **ECC-56 · Major (ops).** The site pipeline mutates the production database twice *before* the new revision deploys: migrations, then a destructive `--prune` cohort seed. A failed or cancelled deploy strands production on the new schema with a pruned cohort while the old revision keeps serving. *Remediate:* expand/contract migrations, or deploy `--no-traffic` → migrate/seed → promote; never prune before the revision expecting it is live.

### Defaults that cost money and breach the data posture

- **ECC-53 · Major (security/ops).** The RAG endpoint script's defaults are a high-cost, DUA-relevant footgun: `INDEX_ID` and machine type default to the 555k-vector index built from real MIMIC-derived notes on e2-standard-16 (~$270/mo), and the documented bare usage deploys it publicly. The mitigation is a comment in a different file, not a safe default. *Remediate:* remove real-corpus defaults, require `INDEX_ID` explicitly, default the small machine, and add the >100k-vector refusal guard the synthetic script already has.
- **ECC-36 · Major (security, cross-section §4/§5).** The Vector Search index endpoint is created with `public_endpoint_enabled=True` — internet-reachable, gated only by IAM, inconsistent with the private agent/MCP posture — and combined with ECC-53, an unnecessary exposure and data-governance risk. *Remediate:* private endpoint (PSC/VPC), or enforce that only synthetic indexes reach the public endpoint via a vector-count guard in the shared deploy path.
- **ECC-54 · Major (ops).** The feature-store deploy path creates an always-on Bigtable-backed FeatureOnlineStore by default (~$0.65+/hr) — and `teardown.py`, the designated cost lever, does not know it exists. The canonical teardown reports billing stopped while Bigtable keeps metering. *Remediate:* add it to teardown's inventory, or delete the likely-superseded FeatureView path; make creation opt-in.
- **ECC-49 · Minor (ops).** Teardown matches index endpoints by the prefix `readmission`, so a future non-demo resource sharing the prefix would be undeployed and deleted. *Remediate:* exact display-name matching (or allowlist) with a confirmed listing.

### The image-provenance guarantees don't hold

- **ECC-55 · Major (ops).** The CPR image's content-addressing is false: the tag hashes the Dockerfile, predictor, and requirements, but the Dockerfile pulls a mutable base and force-reinstalls an unpinned SDK floor — so the same hash yields materially different images, stale caches are reused forever, and a forced build silently changes serving behavior under the same tag. *Remediate:* pin the base by digest and the SDK exactly within the hashed inputs; drop the force-reinstall.
- **ECC-59 · Minor (correctness).** Models are registered against a mutable `:latest` serving container, so a model redeployed after teardown may serve on a different container than it was validated on — undermining the provenance the registry exists to provide. *Remediate:* pin to a versioned tag or digest.

### IAM and secrets hygiene

- **ECC-58 · Minor (security).** No Cloud Build config declares a `serviceAccount`, so builds run as the project default SA — which the site pipeline requires to hold run-admin and actor rights on `website-sa`. Any build submission in the project can therefore execute arbitrary code as an identity that deploys the production site and runs DB-mutating jobs. *Remediate:* a dedicated deploy SA with minimal roles per pipeline; image-only builds on a registry-write-only SA.
- **ECC-51 · Minor (security).** No rotation strategy: Secret Manager reads pin `versions/latest`, so a rotated secret takes effect only on the next redeploy, and no rotation workflow exists. *Remediate:* pin versions where appropriate; document the rotate-then-redeploy behavior and a procedure.
- **ECC-48 · Minor (security).** The model-registration script hardcodes a default bundle URI embedding real resource IDs (project number, run ID, model ID) plus the project — internal topology in source, tying ECC-15. *Remediate:* remove the default; require `BUNDLE_URI`.
- **ECC-50 · Minor (ops).** The Langfuse env file is typo'd — `.env.lanfuse`, missing a 'g'. Gitignored and mode 600, so no secret is committed (a genuine positive), but any future dotenv loader expecting the correct name silently won't find the keys. *Remediate:* rename; keep gitignored.

## Remediation Scope

**Summary.** The strategic read mirrors §1 but one level up the stack: the *deployed* system is well-postured — private services, least-privilege runtime SA, Secret Manager, an honest cost lever — but the *path* to it is console state, permissive defaults, and mutable images, so every recreate-from-repo is a roll of the dice. The recommended order is (1) **make the repo the source of truth and fail closed** — ECC-46, ECC-15, and ECC-57 share one fix shape (no production defaults, required env, config codified in the deploy step) and together eliminate the scenario where a routine recreate becomes a public debug site or a wrong-project operation; (2) **make deploys non-destructive** — ECC-47's deploy-first ordering and ECC-56's traffic-gated migration sequencing, since both currently guarantee windows of outage or stranded state; (3) **defuse the cost and DUA footguns** — ECC-53's real-corpus defaults, ECC-36's public endpoint, ECC-54's invisible Bigtable meter, and ECC-49's prefix-matched teardown; (4) **pin the supply chain** — ECC-55 and ECC-59; (5) **sweep the hygiene minors** — build SA, rotation, hardcoded bundle, the typo'd env file.

**Detail.** The source-of-truth cluster resolves with a fail-closed environment switch, every runtime variable declared in each cloudbuild deploy step (secrets via `--set-secrets`), committed agent/MCP deploy configuration, a single shared project/location config module consumed by all deploy scripts, and a drift check comparing deployed state against the repo — which also retires the recreate-from-file failure mode the backlog names explicitly. Deploy safety is two ordering inversions: the CPR script deploys the new model at full traffic before undeploying stale ones and records enough config to roll back, while the site pipeline adopts expand/contract migrations or the `--no-traffic` → migrate/seed → promote sequence, with the prune step moved after promotion. The footgun cluster is default-removal work: required `INDEX_ID` with the small machine default and the synthetic script's vector-count refusal guard hoisted into the shared deploy path, a private (or guard-enforced) index endpoint, FeatureOnlineStore either registered in teardown's inventory or deleted outright, and exact-name teardown matching with a confirmed listing. Supply-chain pinning is digest-pinned bases and exact SDK versions inside the content hash, plus a versioned serving-container tag at registration. The minors are each small, independent changes: per-pipeline deploy service accounts in the cloudbuild configs, a documented rotation procedure acknowledging the redeploy-to-take-effect behavior, a required `BUNDLE_URI` with the hardcoded default removed, and the one-letter rename of the Langfuse env file.
