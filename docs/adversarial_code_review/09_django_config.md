# §9 — Django Config

## Scope

This section covers the site's configuration layer in `danielmherman/danielmherman/` — `settings.py`, `urls.py`, `asgi.py`, `wsgi.py` — plus `manage.py`. It is the last section of the review, and deliberately narrow: most config-level risk was already captured where it bites — the ENVIRONMENT/DEBUG fail-open (S1-01), session expiry (S1-04), HSTS (S1-12), the CKEditor allow-all and public-read ACL (S1-13), the missing CSP (S6-10), the CVE sweep (S1-16), the root container (S1-14). What §9 adds is the *configuration-completeness* view: read the config as a whole and ask whether an operator recreating this service from the repo alone would arrive at a working, secure deployment.

The settings module is env-driven: a single `ENVIRONMENT` variable gates the production posture. In production it pulls `SECRET_KEY` and the database password from Secret Manager, runs Postgres over a Cloud SQL socket (SQLite locally), serves manifest-hashed static files through WhiteNoise, stores media in GCS with a public-read default ACL, and enables the security block — SSL redirect, secure cookies, proxy header. Channels is configured with an in-memory channel layer unless `REDIS_HOST` is set; `asgi.py` routes HTTP only (no WebSocket routed today). Logging goes to stdout for Cloud Logging; password validators are present; the clock is UTC. The structural reality underneath all of this — the thread §9 pulls on — is that the entire runtime configuration depends on env vars that are not committed or enumerated anywhere, and whose defaults are local-dev values.

## Adversarial Review Pass

§9 ran under the **cross-check protocol**: the adversarial pass read the primary pass's Understand document and tried to falsify it against the code. It independently confirmed three existing findings (S1-01, S1-12, S1-13), added five new items, and upgraded the headline finding — the missing fail-fast — from Minor to Major on the strength of a failure mode the primary pass had not traced. Seven findings resulted (S9-01…S9-07), and they share one theme: **configuration that fails confusingly at runtime rather than loudly at boot**.

### Missing config fails at runtime, not at boot

- **S9-01 · Major (ops).** No startup-time config validation. The settings never check that production env vars are present and consistent, and each absence fails in its own confusing way: a missing `CLOUD_SQL_CONNECTION_NAME` makes the database host silently the literal `/cloudsql/` — the instance boots, passes health checks, and 500s on the first query with an opaque psycopg2 error; a missing `GS_BUCKET_NAME` silently defaults to `danielmherman-media`; a missing `CSRF_TRUSTED_ORIGINS` makes every POST 403; a missing `ALLOWED_HOSTS` yields 400s; a missing `GOOGLE_CLOUD_PROJECT` produces a `projects/None/...` Secret Manager failure. (Secret Manager itself is the one component that *does* fail fast at boot.) Ties S1-01. *Remediate:* a production startup check that raises `ImproperlyConfigured` on any missing required var — `CLOUD_SQL_CONNECTION_NAME`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `GOOGLE_CLOUD_PROJECT`, `GS_BUCKET_NAME`.
- **S9-02 · Minor (ops).** No single documented list of required env vars. The full set — `ENVIRONMENT`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `CLOUD_SQL_CONNECTION_NAME`, `GS_BUCKET_NAME`, `GOOGLE_CLOUD_PROJECT`, `DEMO_AGENT_URL`, `DEMO_FIXTURE_MODE`, `DEMO_AGENT_TIMEOUT`, `DEMO_DAILY_LIMIT`, `REDIS_HOST` — is uncommitted and unenumerated (the S1-01/ECC-46 theme seen from the config side). Recreating the service from the repo leaves the operator guessing. *Remediate:* ship a config manifest (`.env.example` or a documented settings table) alongside the S9-01 fail-fast check.
- **S9-03 · Minor (correctness).** Both `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` are parsed with a bare `env.split(',')` — no strip, no empty-entry filtering. `"a.com, b.com"` yields `' b.com'`, which never matches and 400s; an empty-string env yields `['']`; trailing commas produce empty entries; for CSRF, a whitespace-prefixed origin silently fails the match and 403s every POST. *Remediate:* `[h.strip() for h in val.split(',') if h.strip()]` for both.

### Media storage posture

- **S9-04 · Minor (ops).** `GS_DEFAULT_ACL='publicRead'` uses legacy per-object ACLs. If the bucket has — or is ever migrated to — Uniform Bucket-Level Access, every upload 400s, breaking CKEditor image uploads in production. Separately, the hardcoded `MEDIA_URL` silently disagrees with what `storage.url()` actually emits, because django-storages ignores it. Ties S1-13. *Remediate:* drop `GS_DEFAULT_ACL`, set `GS_QUERYSTRING_AUTH=False`, and grant public read via bucket IAM.

### Dependency hygiene in the production image

- **S9-05 · Minor (security/ops).** Dead and stale dependencies ship in the prod image: `django-ckeditor==6.7.3` is the CKEditor **4** package — unmaintained upstream, bundling a CKEditor 4 build with known XSS CVEs — and it is not even in `INSTALLED_APPS`; `bleach==4.1.0` is a 2021 release and apparently unused; `Django==6.0` is pinned to the bare `.0` release, excluding every 6.0.x security patch. Ties S1-16. *Remediate:* remove `django-ckeditor` and `bleach` if truly unused; pin Django to a 6.0.x patch release.

### Observability and dev serving

- **S9-06 · Minor (ops).** LOGGING names the `django`, `django.request`, and `content` loggers but omits `demo` — the clinical console that calls the private agent and most needs telemetry. Its INFO logs — agent latency, quota decisions, fixture-vs-live — are dropped in production. *Remediate:* add a `'demo'` logger mirroring `'content'`.
- **S9-07 · Minor (correctness).** In DEBUG, `static(STATIC_URL, document_root=STATIC_ROOT)` serves from `staticfiles/` — collectstatic output that is stale or absent locally — and under local uvicorn can serve hashed names against a stale tree while templates emit unhashed ones. Dev-only, low impact; WhiteNoise already handles static. *Remediate:* drop the line and rely on WhiteNoise with `WHITENOISE_USE_FINDERS=True` in dev.

## Remediation Scope

**Summary.** §9 confirms the strategic read from §1 rather than complicating it: the configuration is coherent when every variable is present, and treacherous when any is absent. The cross-check's contribution was to show *how* treacherous — the `/cloudsql/` failure mode passes boot and health checks and only surfaces on the first real query, which is exactly the class of defect a fail-fast exists to prevent, and is why S9-01 was upgraded to Major. The remediation shape is correspondingly simple: (1) **make the config fail closed and fail loudly** — S9-01's `ImproperlyConfigured` check and S9-03's parsing hygiene are one settings-module change, and S9-02's manifest is its documentation twin, all executing naturally with the S1-01 fail-closed work; (2) **modernize the storage posture** — S9-04 lands with §6's content remediation; (3) **sweep the hygiene minors** — the dead dependencies, the missing logger, the dev static line.

**Detail.** The fail-fast is a short block at the bottom of the production branch of settings: enumerate the five required vars, raise `ImproperlyConfigured` naming every one that is missing, and normalize the comma-split lists with strip-and-filter so a stray space can never manifest as a fleet-wide 403. The config manifest is a committed `.env.example` (or settings table) enumerating all eleven variables with their semantics and safe defaults — the artifact S9-02 identifies as the difference between a reproducible service and tribal knowledge. The storage change drops the legacy ACL in favor of bucket-level IAM and unsigned URLs, removing the Uniform Bucket-Level Access time bomb and the `MEDIA_URL` drift in one move; it should be sequenced with §6 since it touches the same upload path as S1-13. The remaining items are each one-line-scale: delete two unused packages and tighten the Django pin to a patched 6.0.x (re-running the S1-16 audit afterward), add the `demo` logger so the highest-value telemetry in the system actually reaches Cloud Logging, and remove the DEBUG static route in favor of WhiteNoise finders.
