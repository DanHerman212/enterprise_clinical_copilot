## 2. Preconditions — check these before running anything

1. **Endpoints up.** Prediction endpoint and RAG index endpoint must be live.
   `python -m mlops.serving.deploy_check` or a single `/risk` call returning a probability.
2. **Image built from a commit, not a working tree.** `git status --porcelain` must show nothing
   that ships. Build with `--substitutions=_TAG=$(git rev-parse --short HEAD)` so
   `commit=<sha>` on the image is true.
3. **Case files current.** `evaluation/agent/results/cases_82.json` (82) and
   `cases_outpatient.json` (5) are regenerated by `build_census.py` at job start; Suite 2's
   `suite2_cases.json` is baked into the image — editing it requires a rebuild (known debt, §6).
4. **Langfuse clean or scoped.** Traces from failed runs are the reader's problem. Purge by tag
   before a run that matters, or accept that the dashboard mixes runs — every row is tagged
   `run:<tag>`.
5. **Judge quota.** Three samples per turn × 24 turns × repeated runs exhausts the Gemini quota
   (observed `429 RESOURCE_EXHAUSTED`). Either `JUDGE_SAMPLES=1` for cheap iterations, or run
   samples sequentially, or request a quota increase before a census (656 turns × 3 = 1,968 calls).

**Read the result from the status condition, never from a shell exit code through a pipe:**

| Gate | Threshold |
| :--- | :--- |
| Route coverage | all five commands execute and reach their tool — hard fail otherwise |
| Structural assertions | zero failures (envelope facts, not grading) |

## 5. Open blocker — the judge is not yet a trustworthy instrument

Measured on identical answers (24 turns, two complete runs at `JUDGE_SAMPLES=3`):

| Condition | Pass rate | Per-turn verdict stability |
| :--- | :-- | :-- |
| single sample | 13/23 = 0.565 | 3 of 24 verdicts changed between runs (**12.5%**) |
| 3-sample consensus, run 1 | 11/24 = **0.4583** | — |
| 3-sample consensus, run 2 | 11/24 = **0.4583** | 2 of 24 verdicts changed (**8.3%**) |

Three conclusions, in order of importance:

1. **The aggregate is now reproducible; the per-turn verdicts are not.** Two runs produced the
   identical pass rate (0.4583) with *different* failing turns — one FAIL→PASS flip and one
   PASS→FAIL flip cancelled out. So "the agent passes 46% of turns" is a number you can act on;
   "turn X failed" is not, and neither are per-turn scores attached to Langfuse.
2. **Consensus made the judge stricter, not merely steadier.** 0.565 → 0.4583. Median plus
   fail-closed safety escalation. Every threshold must be re-based against the new judge.
3. **8.3% is above the 2% target.** Median-of-3 reduced instability from 12.5% to 8.3% and fixed
   the aggregate, but did not make an individual turn reproducible. Dimension medians drift more
   than verdicts: across two runs, `grounding` changed on 5 of 24 turns, `fidelity` on 4,
   `citation` on 4. Raising to 5 samples would tighten it at ~1.7× the quota cost.

**Sample-size arithmetic that matters more than the judge:** the pilot is 23 judged turns.
At p=0.9, the standard error is `sqrt(0.9 × 0.1 / 23) ≈ 0.063` — a 95% interval of roughly
**±12 points**. No amount of judge tuning fixes that; the *sample* is too small to certify 0.90.
The census is 656 turns: `sqrt(0.09/656) ≈ 0.012`, about **±2.3 points**. The release decision
belongs to the census, and the pilot should be treated as a smoke test with a much lower bar
(e.g. 0.70) rather than a 0.90 gate it cannot statistically meet.

## 6. Known debts (each has cost time already)

1. **Case files baked into the harness image** — a one-line data edit costs a build.
2. **Failed gates do not purge their own traces** — scores and traces are written before the gate
   runs. Design noted; not built.
3. **Image tags are nicknames** (`pilot2`) unless `_TAG` is set to the SHA.
4. **No build trigger yet.** The GitHub connection `danielmherman` exists and both repos are
   attached; creating the trigger needs the Console flow (2nd-gen, OAuth + auto IAM) because the
   CLI path demands a fully-qualified repository _and_ a trigger service account.
5. **Orphaned ClickHouse rows** — ~1,860 `observations` from deleted traces.
6. **Langfuse purging must be datastore-level.** The REST delete only queues; the worker drains at
   ~1 row / 2 min. Use `ALTER TABLE … DELETE` in ClickHouse.

## 7. Post-mortem agenda (for after release)

Not a blame list — a process list. Evidence for each item is in `07`, `08` and `09`.

1. **Nine builds in one day**, none requested by the user. Root cause: deploys used as the
   feedback loop, and case data inside the image. Countermeasure: contract tests before build;
   data mounted, not baked; push-triggered builds only.
2. **Symptom-by-symptom patching.** S2-16/17/18 fixed while S2-19 kept the same wrong
   expectation; `WIRE_COMMAND` guessed for two of five entries. Countermeasure: a "sweep for
   siblings" step, enforced by a test that asserts a rule holds across every case of a shape.
3. **Reporting that outran the evidence.** `EXIT=0` read from a piped command; "Gate 1 passed"
   stated from `succeededCount`. Countermeasure: verdicts come from the execution's status
   condition, and a report names the number it read.
4. **Observability polluted by debugging.** Three scored sets accumulated with no explanation.
   Countermeasure: failed gates purge their own tag; every scored run is announced when it lands.
5. **Governance gap.** Images built from uncommitted code; no trigger; no dirty-tree guard.
   Countermeasure: §2.2 and §6.4.

## 8. Programmatic target state

The goal is a process where the only human acts are approving a rubric change and reading a
verdict:

```
push to main
  └─ Cloud Build trigger (evaluation/**)  → build harness image@SHA, deploy jobs
       └─ execution launcher (manual or scheduled)
            ├─ Gate 1 preflight → fail: purge own traces, exit non-zero
            ├─ Gate 2 adversarial + pilot → fail: purge, exit
            └─ Gate 3 census → artifacts to gs://…/runs/census-<sha>/, scores to Langfuse
                 └─ verdict written to a manifest; nothing else is "passed"
```

Non-negotiables for that to be trustworthy: contract tests green before build; judge stability
measured and documented per run (`_samples`, `_agreement` on every judged row); sample size
matched to the threshold being claimed; and one purge policy — a run that fails leaves a log
line, not a dashboard.
